# dsh-tts 输出契约

这份文档只讲一件事：**一次合成到底落下什么文件、每个字段是什么意思、下游怎么读**。
它是本插件与 `video-factory` / `dsh-video-audio` 之间的接口说明。

## 1. 一次 `speak` 落两个文件

```
<outDir>/voiceover.mp3        ← 音频（引擎决定格式：edge 是 24 kHz 单声道 MP3；command 按 outFormat）
<outDir>/voiceover.words.json ← 侧车（同名、同目录，stem + ".words.json"）
```

`outPath` 可以指定音频路径，侧车总是跟着它（`<stem>.words.json`）。扩展名由 provider 决定：
本地引擎写 WAV 时不会得到一个叫 `.mp3` 的文件。

## 2. 侧车字段

```json
{
  "audio": "/abs/path/voiceover.mp3",
  "provider": "edge",
  "voice": "zh-CN-XiaoxiaoNeural",
  "text": "开源语音合成的选择很多。",
  "duration": 4.887,
  "durationSource": "word-boundaries",
  "audioSeconds": 5.448,
  "tailSilenceSeconds": 0.561,
  "timings": "word-boundaries",
  "wordCount": 16,
  "words": [{ "text": "开源", "start": 0.1, "end": 0.42 }],
  "engine": { "voice": "…", "rate": "+0%", "outputFormat": "audio-24khz-48kbitrate-mono-mp3" }
}
```

| 字段 | 含义 | 来源 |
| --- | --- | --- |
| `audio` | 音频绝对路径 | 调用参数 |
| `provider` | 哪个引擎答的 | provider 注册表 |
| `voice` | 实际请求的音色；引擎没有音色概念时是 `null` | 参数 / 配置 |
| `text` | 这次念的原文（便于日后追溯） | 参数 |
| `duration` | **话说到哪**：最后一个词的结束时刻；引擎只报文件长度时，就是那个长度 | 引擎 |
| `durationSource` | `word-boundaries` / `engine-json` / `ffprobe` / `timeline` / `unavailable` | 见下 |
| `audioSeconds` | **文件有多长**：ffprobe 解码得到的时长；没有 ffprobe 时为 `null` | ffprobe |
| `tailSilenceSeconds` | `audioSeconds − duration`，即引擎追加的尾部静音；两者不是同一个量时为 `null` | 计算 |
| `timings` | `word-boundaries` / `engine-json` / `none` | 引擎 |
| `wordCount` | 词数 | 引擎 |
| `words` | `[{text, start, end}]`，秒，三位小数 | 引擎 |

### `durationSource` 为什么必须存在

同一个 `duration` 可能来自三件不同的事：

| 值 | 说的是 | `tailSilenceSeconds` |
| --- | --- | --- |
| `word-boundaries` | 服务端的逐词边界，最后一个词的结束时刻 | 有值（需要 ffprobe） |
| `engine-json` | 本地引擎自己写出的时间戳文件的最后一项 | 有值（需要 ffprobe） |
| `ffprobe` | 只是文件长度；**没人量过话说到哪** | `null`（不是 0） |
| `timeline` | 对话时间线的总长（`dialogue.words.json`） | `null` |
| `unavailable` | 引擎没报，也没有 ffprobe | `null` |

把 `ffprobe` 的时长当成"话说完的时刻"会让每一句字幕都多出这段尾部静音，
所以这两种情况在字段上就是分开的，而不是靠调用方猜。

## 3. 一次 `dialogue` 落两份额外文件

```
<outDir>/lines/001-host-a.mp3     ← 每行一个文件（stem = 序号-说话人）
<outDir>/lines/001-host-a.words.json
<outDir>/dialogue.json            ← manifest：clips + lines + voices
<outDir>/dialogue.words.json      ← 全局词级时间戳（已按各行起点平移）
```

### `dialogue.json` 的形状

```json
{
  "kind": "dsh-tts/dialogue",
  "provider": "edge",
  "voices": { "host-a": "zh-CN-XiaoxiaoNeural", "host-b": "zh-CN-YunxiNeural" },
  "gapSeconds": 0.35,
  "tailPadSeconds": 0.12,
  "tailSeconds": 0.5,
  "totalSeconds": 3.219,
  "lineCount": 2,
  "sharedVoices": [],
  "unknownSpeakerTokens": [],
  "clips": [
    { "source": "…/lines/001-host-a.mp3", "at": 0, "until": 1.144, "speaker": "host-a", "text": "欢迎收听。", "duration": 1.024 },
    { "source": "…/lines/002-host-b.mp3", "at": 1.374, "until": 2.719, "speaker": "host-b", "text": "我们今天聊点什么？", "duration": 1.225 }
  ],
  "lines": [{ "speaker": "host-a", "audio": "…", "at": 0, "duration": 1.024, "until": 1.144, "chars": 5, "voice": "…", "words": 5 }],
  "words": [{ "text": "欢迎", "start": 0.05, "end": 0.4, "speaker": "host-a" }]
}
```

排版的算术（`planTimeline`）：

```
line[i].at    = line[i-1].at + line[i-1].duration + gapSeconds        （第一行 at = 0）
line[i].until = line[i].at + line[i].duration + tailPadSeconds        （切掉尾部静音，保留语音衰减）
totalSeconds  = 最后一行的 until + tailSeconds
word.start    = 该行 at + 词在本行内的 start
```

每一行都必须有可用时长：引擎报，或者 ffprobe 量。两者都没有时 `dialogue` **在合成任何一行之前**就拒绝，
因为一个猜出来的起点会让它之后的每一行都错位，而在成品里听起来只是"字幕和声音对不上"。

### `verification`：拼之前先自己核对一遍

```json
"verification": {
  "linesChecked": 3,
  "linesUnchecked": 0,
  "everyClipWithinItsFile": true,
  "violations": [],
  "note": "…"
}
```

每一行在合成时都量过文件长度（`audioSeconds`），所以这里能免费核对一件事：
**要截取的片段长度（`until − at`）是否落在该行文件之内**。注意比的不是 `until` 与文件长度——
`until` 是拼装时间线上的绝对位置，而每行的文件都从 0 开始；第二行从 2.35 s 处开始、文件只有 1.3 s
是完全正常的，从 1.0 s 的文件里截 1.3 s 才不正常。`violations` 报的是后者：

```json
"violations": [{ "speaker": "host-b", "clipSeconds": 1.337, "audioSeconds": 1.0 }]
```

`everyClipWithinItsFile` 是**三值**的：`false` 表示有片段超出文件，`true` 表示每一段都量过且都在文件内，
**`null` 表示一行都没量过**（`measure:false` 或这台机器没有 ffprobe）——不是"没问题"。
`linesUnchecked` 说明有几行是这样。

## 4. 下游怎么读

| 下游 | 读什么 | 怎么用 |
| --- | --- | --- |
| `video_narrate {action:"to_cues"}`（video-factory） | `words`（裸数组或 `{words:[...]}` 都接受） | 断句成字幕条 → SRT → 烧录样式 |
| `audio_build {action:"assemble"}`（dsh-video-audio） | `dialogue.json` 的 `clips` | 采样级拼接，落点自带解码核对 |
| `audio_measure`（dsh-video-audio） | 音频文件 | 响度 / 电平 / 削波 / 帧链完整性等客观测量 |
| 人 | `durationSource` 与 `tailSilenceSeconds` | 判断这个 `duration` 能不能直接拿来对时码 |

`audio` 为 `null` 的情况只有一处：`dialogue.words.json`。对话的音频不是单个文件，所以那里的
`durationSource` 是 `timeline`，音频来自 `clips`。

## 5. 兼容承诺

- 侧车**只增字段，不改含义**；下游不认识新字段时按忽略处理即可。
- `words[]` 的元素永远是 `{text, start, end}`，秒，升序；`dialogue.words.json` 的元素多一个 `speaker`。
- 时间戳精度是毫秒（三位小数）；服务端 100 ns 刻度在转换处就取整，不留给下游。
- `timings:"none"` 时 `words` 是空数组，而不是缺字段。

## 6. 读这些文件的注意事项（Windows）

JSON 一律写成 **UTF-8 无 BOM**，Node 与 ffmpeg 读它没有问题。但 **Windows PowerShell 5.1 的
`Get-Content -Raw` 会按系统 ANSI 代码页（简体中文机器上是 936）解码无 BOM 的 UTF-8 文件**，
于是中文在控制台里变成乱码、`ConvertFrom-Json` 可能直接报错：

```powershell
# 会乱码
$m = Get-Content -Raw out\podcast\dialogue.json | ConvertFrom-Json
# 正确
$m = Get-Content -Raw -Encoding UTF8 out\podcast\dialogue.json | ConvertFrom-Json
```

同样地，**不要用 `Get-Content -Raw` + `Set-Content -Encoding UTF8` 去原地改写本插件的源文件**：
这个组合在 PS 5.1 下会把中文重编码成乱码，兄弟仓库 `dsh-video-audio` 的四个核心模块就是这么被毁的
（见其 `docs/事故记录.md`）。
