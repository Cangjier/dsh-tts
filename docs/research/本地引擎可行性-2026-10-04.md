# 本地引擎可行性核查（2026-10-04）

这份文档回答一个问题：**下一步给 `dsh-tts` 加一个本地开源引擎，走哪条路？**
结论都附出处；标「实测」的是在本机直接跑出来的数字，不是文档推断。

> **为什么不在这里附原始副本。** 核查时下载过 edge-tts 的源码副本（GPL-3.0）与若干 README/模型卡，
> 事后全部删除：把别人的源码逐字抄进一个 MIT 仓库是许可风险，而这里每一条结论都能由下面的 URL 复现。
> 唯一留下的是基准脚本 `bench-kokoro-cpu.mjs`（自己写的）和这份文档。
> 复现两个关键数字：音色目录用 `node src/bin/tts.mjs voices --locale zh`，
> Kokoro 的 CPU 比值用 `bench-kokoro-cpu.mjs`（需要先 `npm i kokoro-js`）。

## 一、现状：已经接进来的两种

| provider | 状态 | 证据 |
| --- | --- | --- |
| `edge` | 已在用，本机可用 | 本插件 live 测试：16 词 / 4.887 s 语音 / 5.448 s 文件 / 尾部静音 0.561 s；音色目录 322 个，zh 14 个 |
| `command` | 已实现，未接具体引擎 | 模板 + 占位符；任何能写文件的命令行引擎都能用 |

## 二、Edge read-aloud 端点的核对结果

- 音色列表：`https://speech.platform.bing.com/consumer/speech/synthesize/readaloud/voices/list?trustedclienttoken=<公开常量>`，
  见 `raw/constants.py`、`raw/voices.py`。
- **实测**：不带头 → 200；伪造 `Sec-MS-GEC` → 200；token 改成全 0 → 401。
  即当前 `voices/list` **只校验 token，`Sec-MS-GEC` 不是必需**——本插件的 `httpsGetText` 因此不签名，这是刻意的。
- JSON 顶层就是数组（本机取到 322 条），字段 `Name / ShortName / Gender / Locale / LocaleName / SuggestedCodec / FriendlyName / Status / VoiceTag{ContentCategories, VoicePersonalities}`，
  没有顶层 `Personalities`。本插件的 `parseVoiceList` 就是按这个形状防御性解析的。
- 中文音色 **14 个**（本插件的 `voices --locale zh` 实测一致）：zh-CN 6 个（Xiaoxiao / Xiaoyi / Yunjian / Yunxia / Yunxi / Yunyang）、
  `zh-CN-liaoning-XiaobeiNeural`、`zh-CN-shaanxi-XiaoniNeural`、zh-HK 3 个（HiuGaai / HiuMaan / WanLung）、zh-TW 3 个（HsiaoChen / HsiaoYu / YunJhe）。
- 已知坑（都对得上本插件的实现）：403 与时钟偏差/签名窗口有关（`raw/drm.py` 用响应的 `Date` 头自动校正）；
  中国大陆有专门的 403 报告；代理是真实需求（`list_voices` 显式有 `proxy` 参数，aiohttp 用 `trust_env=True`）——
  本机 `systemProxy()` 返回 `127.0.0.1:7897`，两个方向都走 CONNECT 隧道；
  音色列表里存在但合成端间歇报 “No audio was received” 的报告，所以 `tts_setup {action:"check"}` 才是"可用"的证据，`status` 不是。

## 三、Kokoro-82M：许可最好，但中文这条路的结论是「先走 command」

- 权重 [hexgrad/Kokoro-82M](https://huggingface.co/hexgrad/Kokoro-82M) **Apache-2.0**，中文版 [Kokoro-82M-v1.1-zh](https://huggingface.co/hexgrad/Kokoro-82M-v1.1-zh) 同为 Apache-2.0；
  代码 [hexgrad/kokoro](https://github.com/hexgrad/kokoro)、[misaki](https://github.com/hexgrad/misaki)、
  [kokoro-js](https://www.npmjs.com/package/kokoro-js) 都是 Apache-2.0，[HeadTTS](https://github.com/met4citizen/HeadTTS) MIT。
- 官方推荐路径是 **PyTorch**（`pip install kokoro` + `KPipeline`）；Node 侧官方有 `kokoro.js` → `kokoro-js` → `onnxruntime-node`。
- **关键实测（代理了这个判断）**：`kokoro-js@1.2.1` 只注册 28 个英文音色，传 `zf_xiaoxiao` 直接抛
  `Voice ... not found`；它的 `phonemize` 只接受 `"a"/"b"`。包内虽然带着 `zf_*.bin`，代码里查不到 → **中文走不通**（`raw/kokoro_js_phonemize.js`、`raw/kokoro_js_voices.js`）。
- 中文音色：v1.0 共 8 个（`zf_xiaobei / zf_xiaoni / zf_xiaoxiao / zf_xiaoyi / zm_yunjian / zm_yunxi / zm_yunxia / zm_yunyang`）；
  v1.1-zh 共 103 个（中文 100 个）。
- 中文 G2P 依赖在 Python 侧：`misaki[zh]` = jieba + pypinyin + cn2an + ordered-set + pypinyin-dict。
  **所以纯 Node 中文 Kokoro 的拦路虎不是模型，是前端文本处理。**
- 体积（实测 HF 字节数）：ONNX v1.0 `model.onnx` 325 MB / fp16 163 MB / q8 92 MB；v1.1-zh 339 MB / fp16 164 MB / int8 127 MB。
- 时间戳：HeadTTS 用 `Kokoro-82M-v1.0-ONNX-timestamped`，输出 `words[] / wtimes[] / wdurations[] / visemes[]` 等，
  但自述 **English is currently the only supported language**；`Kokoro-FastAPI` 的 `/dev/captioned_speech` 另有一套词级 timestamps。
  **中文词级时间戳没有现成方案** → 走强制对齐（WhisperX / MFA），这与本插件 `command` provider 的 `timings:"none"` 设计一致。
- CPU 速度（实测，注意本机不是 4 核）：本机 2×Xeon 8378C = **8 物理核 / 16 线程**，
  `kokoro-js` + `onnxruntime-node` + q8，英文 505 字符 → 26.4 s 音频耗时 28.5 / 29.3 / 30.0 s，
  即 **每 1 秒音频约 1.08–1.14 秒计算**（基准脚本见 `bench-kokoro-cpu.mjs`）。
  公开的另一份（2 核 ARM，fp32）是 x0.91–0.93。**4 核机器上的实测没有查到，本机也没有 4 核配置。**

## 四、这对下一步意味着什么

1. **要马上拿到本地中文语音**：走已经实现的 `command` provider，把 Python 侧的 Kokoro / Piper / GPT-SoVITS 包成一条命令。
   代价是 `timings:"none"`，字幕要靠强制对齐——这条路今天就能通，且不需要给插件加任何依赖。
2. **要一个纯 Node 的原生 Kokoro provider**：模型和推理都不是问题（`onnxruntime-node` 实测可用），
   问题在中文 G2P 与中文音色表；在有人把 misaki 的中文前端搬到 JS 之前，这条路会把插件绑死在 Python 上，
   而那正是 `command` 已经解决的事。
3. **要中文词级时间戳**：无论哪个本地引擎，都得接强制对齐；这是 `tts_guide {action:"rules"}` 里
   `missing-timings-are-named` 那条规则的由来，不是临时方案。
4. **速度预期**：本机 8 核 q8 约 1.1× 实时；一条 20 分钟的播客要算 20 分钟以上，
   而这台机器还要同时跑 DSH。要么接受，要么租 GPU，要么用云引擎。
